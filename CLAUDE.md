# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

HarmonySmiles is a dental clinic reservation system with three independent top-level parts (no root package.json tying them together):

- `backend/` — Node.js/TypeScript/Express API backed by PostgreSQL. Every route in the spec is implemented (see "Implementation status" below); still actively evolving.
- `frontend/` — static HTML/CSS/Bootstrap 5 marketing site, no build step. The public booking page (`page/bookappointment.html`) and the admin dashboard (`page/admin/`) are wired to the backend via plain `fetch()` calls; the rest of the marketing pages are still static/unwired.
- `database/schema.sql` — hand-written SQL schema, applied manually to Postgres (no migration tool).

The full intended design (API routes, business rules, DB schema) is specified in `.agents/workflows/harmonysmiles.md`. Treat it as the design intent, not as a description of current code — much of it is not built yet.

## Commands

All commands run from `backend/`:

- `npm run dev` — `tsx watch src/server.ts` (tsx has built-in watch mode, no nodemon needed)
- `npm run build` — `tsc`, emits to `backend/dist/` (checked into git)
- `npm start` — runs the built `dist/server.js`

The package is ESM (`"type": "module"` in `package.json`), matching the `.js`-suffixed relative imports used everywhere (required by `"module": "nodenext"` in `tsconfig.json`) — don't reintroduce `ts-node`, its ESM loader hooks don't work against current Node versions and will silently fail to resolve `.js` specifiers back to `.ts` source files.

There is no test framework, test script, or lint config anywhere in this repo — don't invent `npm test`/`npm run lint` commands.

Required env vars (see `backend/.env`, not committed): `PORT`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `JWT_SECRET`. `src/utils/jwt.ts` throws at import time if `JWT_SECRET` is missing — fail fast rather than silently signing tokens with an undefined secret. `ADMIN_USERNAME`/`ADMIN_PASSWORD` are only needed to run `npm run seed` (`backend/seed.ts`), not for the server itself.

## Backend architecture

Layering flows `routes/` → `controllers/` → `services/` → raw `pg` queries via `src/config/db.ts`. No ORM is used anywhere — all SQL is hand-written with parameterized queries (`$1`, `$2`, ...).

- `src/app.ts` builds and exports the Express `app` (middleware + routes); `src/server.ts` imports it and calls `.listen()`. Keep that split — don't move `app.listen` back into `app.ts`.
- `src/config/db.ts` exports a pooled `query<T>()` for simple queries, `getClient()` for a raw connection, `withTransaction(fn)` which wraps `fn` in `BEGIN`/`COMMIT`, rolling back and releasing the client on any error, and `closePool()` (only used by `seed.ts`, so a one-off script can actually exit instead of hanging on an open connection — the server itself never calls it). Use `withTransaction` for new atomic writes instead of hand-rolling `try/catch/finally`. It also overrides `pg`'s type parser for OID `1082` (`DATE`) to return the raw `'YYYY-MM-DD'` text instead of a JS `Date`: pg's default parser builds `Date`s at **local server-OS midnight**, and since dev boxes here run `Africa/Cairo` (UTC+3, not the app's `Europe/Zurich` clinic time), that JS `Date` then serializes to a UTC ISO string a day behind (`appointment_date`s were shipping to the frontend shifted back one calendar day, e.g. an admin "Today"/"Tomorrow" filter would show the wrong bucket). `appointments.appointment_date` is the only `DATE` column in the schema; `Appointment.appointment_date` in `appointment.types.ts` is typed `string` to match, and always compare/insert it as a plain `'YYYY-MM-DD'` string, never a `Date` object. `created_at`/`updated_at` are `TIMESTAMPTZ`, genuinely represent instants, and are unaffected/unchanged.
- `src/utils/AppError.ts` is a small `Error` subclass carrying a `statusCode`. Throw it from services for expected, user-facing failures (e.g. booking conflict → 409). Plain `throw new Error(...)` is still fine for "should never happen" cases — it becomes a 500.
- `src/middlewares/error.middleware.ts` is mounted last in `app.ts` and is the only place HTTP status codes get decided for errors: `ZodError` → 400 with per-field issues, `AppError` → its `statusCode`, anything else → 500 (logged server-side via `console.error`). Controllers should just `next(error)` and never set error status codes themselves.
- `src/middlewares/validate.middleware.ts` exports `validate(schema)`, a generic factory that `safeParse`s `{ body, query, params }` against a Zod schema and, on success, replaces `req.body`/`query`/`params` with the parsed (and coerced) output before calling `next()`. Use this for every new validator instead of writing bespoke middleware per route. Note: Express 5 exposes `req.query` as a getter-only accessor (no setter) — the middleware replaces it via `Object.defineProperty`, not plain assignment, or it throws `TypeError: Cannot set property query of #<IncomingMessage> which has only a getter`. `req.body`/`req.params` don't have this problem and are reassigned normally.
- `src/middlewares/validators/*` hold the Zod schemas themselves (shape `{ body: z.object({...}) }` or `{ query: z.object({...}) }`), consumed by `validate()` at the route level — see `appointment.validator.ts` and `general.validator.ts` for the pattern, including the "must be in the future"/"must not be in the past", "clinic must be open that day", and "must be within 1 month" checks done against the clinic's local time (`Europe/Zurich` — the clinic is in Switzerland, not Egypt; if you see `Africa/Cairo` anywhere, that's a stale leftover, not intentional), not server time. Both validators use `src/utils/clinicTime.ts`'s `getClinicNow()`/`CLINIC_TIMEZONE`/`isClinicClosedOn()`/`getMaxBookableDate()` rather than duplicating the day-of-week/date-math logic — add new clinic-local-time checks through those shared helpers. `first_name`/`last_name` in `createAppointmentSchema` require a 3-character minimum (not just non-empty).
- `src/types/*.types.ts` are hand-written interfaces per domain (appointment, patient, admin, auth) — no codegen from the DB schema.
- `src/services/appointment.service.ts::createAppointmentService` is the reference implementation for transactional services: inside `withTransaction`, it does an atomic `INSERT ... ON CONFLICT (phone) DO NOTHING RETURNING id` against `patients` (falling back to a `SELECT` by phone only if the insert hit the conflict), inserts the appointment, and outside the transaction, catches a Postgres `DatabaseError` whose `constraint` is `unique_active_appointment` and rethrows it as an `AppError` (409) with a user-facing message. Follow this pattern for other transactional service functions.
- `src/services/appointment.service.ts::getAvailableSlotsService` backs `GET /available-slots`: queries booked `appointment_time`s for the given date (`status IN ('Pending', 'Confirmed')`), then hands them to the pure `utils/generateSlots.ts::generateAvailableSlots(date, bookedTimes)`, which has no DB access of its own — it just computes free 30-minute slots (10:00–18:00 clinic-local time, Saturday and Sunday fully closed via `clinicTime.ts::isClinicClosedOn()`, past slots excluded for today). Sunday (not Friday) being a closed day is confirmed correct — the clinic is in Switzerland, not Egypt; Saturday is also closed. Both `availableSlotsSchema` and `createAppointmentSchema` additionally reject dates more than 1 month out (`clinicTime.ts::getMaxBookableDate()`, which computes "same day next month" clamped to that month's last day — a naive `getMonth() + 1` on e.g. Jan 31 would otherwise overflow into March since Feb is shorter; fixed this session, and `bookappointment.js` has the matching client-side fix for its own copy of the same 1-month-out calculation).
- `src/services/appointment.service.ts` also owns the admin CRUD surface — `listAppointmentsService`, `getAppointmentByIdService`, `confirmAppointmentService`, `cancelAppointmentService`, `completeAppointmentService`, `noShowAppointmentService`, `deleteAppointmentService` — all plain (non-transactional) queries; all but `createAppointmentService` throw `AppError('Appointment not found', 404)` when the target row doesn't exist. `listAppointmentsService` builds its `WHERE` clause dynamically, only for filters actually supplied (`status` exact match, `search` as `ILIKE` across the joined patient's name/phone, `dateRange` as independent `>=`/`<=` conditions built from whichever bounds `clinicTime.ts::getDateRangeForPreset()` returns), and always orders by `appointment_date, appointment_time` per spec. Every admin read path (`listAppointmentsService`, `getAppointmentByIdService`, `listAppointmentsByPatientIdService`) opens by calling a private `markPastAppointmentsAsNoShow()` — an `UPDATE ... SET status = 'NoShow' WHERE status IN ('Pending', 'Confirmed') AND <date+time is in the past>` — so a patient who never showed up automatically flips to `NoShow` the next time admin data is read after their slot passes. This is a lazy sweep-on-read, not a scheduled job (there's no cron/`setInterval` anywhere in the project) — deliberately, to match the project's "no background-job infrastructure" scope; if that need grows, replace it with a real scheduler rather than adding more read-path side effects. `completeAppointmentService`/`noShowAppointmentService` are the manual counterparts (`PATCH .../complete`, `PATCH .../no-show`) — both gated by `clinicTime.ts::hasAppointmentDateTimePassed()`, throwing an `AppError(409)` if called before the appointment's own date+time has arrived (an appointment can't be marked completed, or marked as a no-show, ahead of when it's actually scheduled to happen). `confirmAppointmentService` additionally catches a `DatabaseError` on `unique_active_appointment` the same way `createAppointmentService` does — re-confirming an old `Cancelled`/`Completed`/`NoShow` appointment can collide with a different appointment that's since taken its date+time slot, and without the catch that surfaces as a raw 500 instead of a clean 409. `cancelAppointmentService`/`completeAppointmentService`/`noShowAppointmentService` don't need the same guard: none of them ever set status to `Pending`/`Confirmed`, so they can't re-enter the partial unique index's protected set. `listAppointmentsByPatientIdService(patientId)` backs the patient profile page — one query for all of a patient's appointments (any status), split in JS into `{ upcoming, past }` by comparing each row's `appointment_date` string against `clinicTime.ts::getClinicTodayISODate()` (string comparison works because `YYYY-MM-DD` sorts lexicographically the same as chronologically).
- `src/services/patient.service.ts::listPatientsService` backs the admin patients table (`GET /admin/patients`) — a plain, non-transactional query over `patients` directly (not joined with `appointments`), with the same optional-`search`/dynamic-`WHERE` pattern as `listAppointmentsService` (`ILIKE` across name/phone/MRN), ordered by `medical_record_number` (i.e. registration order, not alphabetically — a deliberate change from an earlier `last_name, first_name` ordering). The `patients` table only stores `birth_year` (no full DOB); the query derives `age` as `clinic-current-year - birth_year` in SQL (current year passed in via `clinicTime.ts::getClinicNow()`, not the DB server's own clock) and returns `age` instead of the raw `birth_year` — recomputed on every fetch, never persisted, so it's always correct without a yearly update job. `getPatientByIdService(id)` is the same query narrowed to `WHERE id = $1`, throwing `AppError('Patient not found', 404)` when missing — it backs the patient profile page (`GET /admin/patients/:id`) alongside `listAppointmentsByPatientIdService`.
- There is no separate MRN-generation utility — the medical record number is derived in the same `INSERT` as the patient row, from that row's own `id` (via `nextval`/`currval` on `patients_id_seq`), so it can never race or drift from the patient it belongs to.
- `src/utils/clinicTime.ts` also exports `getClinicTodayISODate()` (today as `'YYYY-MM-DD'`), `getClinicNowDateTime()` (today's date **and** time as separate strings, for comparing against `appointment_date`/`appointment_time` columns), and `hasAppointmentDateTimePassed(date, time)` (used by the complete/no-show time gate above). `getDateRangeForPreset` now also accepts `'upcoming'` (today and forward, open-ended — no `to`) and `'previous'` (strictly before today, open-ended — no `from`) alongside the original `today`/`tomorrow`/`week`/`month`, returning `{ from?, to? }` rather than always both bounds.

### Implementation status

Every route in the spec is now implemented and wired end-to-end, reachable over HTTP:
- `GET /health` (`app.ts`, mounted before the `/api` routers, no `validate()`/auth) — returns `200 { status: 'ok' }`. Exists purely for Render's deploy health check, not part of the spec.
- `POST /api/appointments` (`public.routes.ts`) → `validate(createAppointmentSchema)` → `appointments.controller.ts` → `appointment.service.ts` → `errorMiddleware` on failure.
- `GET /api/available-slots?date=YYYY-MM-DD` (`public.routes.ts`) → `validate(availableSlotsSchema)` → `appointments.controller.ts::getAvailableSlots` → `appointment.service.ts::getAvailableSlotsService` → `utils/generateSlots.ts`.
- `POST /api/admin/login` (`admin.routes.ts`) → `validate(loginSchema)` → `auth.controller.ts` → `auth.service.ts` (bcrypt compare + `signToken`) → `errorMiddleware` on failure. Every route registered on `adminRouter` **after** the `login` route is automatically behind `authMiddleware` (mounted via `adminRouter.use(authMiddleware)` right after `login`) — this ordering, not a per-route check, is what makes a newly added admin route protected by default. `authMiddleware` reads `Authorization: Bearer <token>`, verifies it via `utils/jwt.ts`, and attaches the payload to `req.admin` (typed via the module augmentation in `src/types/express.d.ts`). `jwt.ts::signToken`/`verifyToken` both pin `algorithm(s): 'HS256'` explicitly rather than trusting the library default — defense-in-depth, not currently exploitable since there's only ever one symmetric secret in play. `auth.service.ts::loginService` always runs a `bcrypt.compare` — against a fixed dummy hash when the username doesn't exist — instead of short-circuiting on "no such user", so that path can't be distinguished from "wrong password" by response timing (both already return the identical error message; the timing fix closes the side-channel that message-matching alone didn't).
- `GET /api/admin/appointments` (optional `?status=`/`?search=`/`?date_range=today|tomorrow|week|month|upcoming|previous`, `validate(listAppointmentsSchema)`; `date_range` is resolved to a `{ from?, to? }` open-ended-or-not date bound server-side via `clinicTime.ts::getDateRangeForPreset()` — `week` is the current Monday–Sunday ISO week, `month` the current calendar month, `upcoming`/`previous` are open-ended around today, all clinic-local), `GET /api/admin/appointments/:id`, `PATCH /api/admin/appointments/:id/confirm`, `PATCH /api/admin/appointments/:id/cancel`, `PATCH /api/admin/appointments/:id/complete`, `PATCH /api/admin/appointments/:id/no-show`, `DELETE /api/admin/appointments/:id` (all six sharing `validate(appointmentIdParamSchema)`), `GET /api/admin/patients` (optional `?search=`, `validate(listPatientsSchema)`), and `GET /api/admin/patients/:id` (`validate(patientIdParamSchema)`, a separate schema from `appointmentIdParamSchema` purely for a resource-appropriate error message — both just validate a positive-int `id` param) — all in `admin.routes.ts` → `admin.controller.ts` → the admin functions in `appointment.service.ts`/`patient.service.ts`. All protected by the `authMiddleware` ordering above.

`backend/seed.ts` (run via `npm run seed`, requires `ADMIN_USERNAME`/`ADMIN_PASSWORD` env vars) creates the first admin account — bcrypt-hashed, `ON CONFLICT (username) DO NOTHING` so it's safe to re-run. It's outside `tsconfig.json`'s `include` (`src/**/*`) by design, same as the rest of `src/`'s stubs were — run directly via `tsx`, not compiled by `npm run build`.

No empty stubs remain in `backend/src/` — every file listed in `ARCHITECTURE.md` is now implemented.

All comments and user-facing strings (API response `message` fields, thrown `Error` messages) are English — kept short, one line where possible. This file previously claimed user-facing strings were "in Arabic by design"; that was a leftover from the same stale Egypt assumption behind the old `Africa/Cairo`/Friday-closed mistakes and has been confirmed wrong — the clinic is in Switzerland, English is correct.

## Database

Schema lives in `database/schema.sql` and is applied manually (no migration tooling — if you change the schema, update this file and note that it needs to be re-run).

The load-bearing, non-obvious piece: `unique_active_appointment` is a **partial unique index** on `appointments (appointment_date, appointment_time) WHERE status IN ('Pending', 'Confirmed')`. This prevents double-booking a slot while still allowing it to be rebooked once the prior appointment is cancelled/completed/no-show — it's what `createAppointmentService` catches by constraint name to produce the "slot already booked" error.

`patients.phone` is `UNIQUE` — the service layer relies on this for its `ON CONFLICT (phone)` upsert, so don't drop it.

`appointments.patient_id` FK is `ON DELETE RESTRICT` (a patient with existing appointments can't be deleted outright) — this matches `.agents/workflows/harmonysmiles.md` as of the last edit; if you see `ON DELETE CASCADE` mentioned anywhere else, that's stale.

## Frontend

Plain static site: pages live under `frontend/page/*.html` (e.g. `veneersection.html`, `implantsection.html`, `orthodonticsection.html`, `cleaningsection.html`), styles under `frontend/style/`, entry point `frontend/index.html`. No bundler, no package.json, no build step — edit the HTML/CSS directly. `frontend/README.md`'s file-structure section is stale (describes files like `services-cosmetic.html`/`team.html` that don't exist) — trust the actual directory listing over that README.

Two parts of the frontend are wired to the backend via plain `fetch()` (no framework, no build step — each page loads its own small `.js` file):
- `frontend/page/bookappointment.html` + `bookappointment.js` — the real public booking form. Loads live slots from `GET /available-slots` whenever the date changes, then `POST`s to `/appointments` with exactly the fields `createAppointmentSchema` expects (optional fields are omitted entirely when empty, since the backend's `.strict()` schemas reject unexpected/empty-string keys). Every page's "Book an Appointment" nav link (main nav + mobile offcanvas, across all pages) points here now, not to `contactus.html` (which is still just a non-functional generic contact form). The phone field is a country-code `<select>` (populated from `countryCodes.js`'s `COUNTRY_CODES`, sourced from every UN member state + Vatican City) plus a local-number `<input>`; the two are concatenated client-side before being sent as the single `phone` string the backend expects. `bookappointment.js` also does client-side pre-validation mirroring the backend rules — name fields require 3+ characters, phone must be `+` plus 10-15 digits (matches `appointment.validator.ts`'s `/^\+?[0-9]{10,15}$/` exactly; it used to allow 9 digits, which the backend then rejected with a confusing error), birth year and gender are both required, `appointment_date` rejects Saturdays/Sundays and anything past 1 month out — via a Bootstrap `is-invalid` class (there's no per-field `.invalid-feedback` text for any field; the generic error banner carries the message) toggled in a `validateForm()` gate before the `fetch` call; this is UX only, the backend validators are still the enforcement boundary.
- `frontend/page/admin/` — `login.html`/`login.js` (posts to `/admin/login`, stores the JWT in `localStorage`), `admin-common.js` (shared by every logged-in admin page — the `getToken()` redirect guard, `escapeHtml()`, and the logout button handler; not loaded on `login.html`, which has neither), `dashboard.html`/`dashboard.js` (appointments table — filterable by status and by a date-range preset (`Previous`/`Upcoming`/`Today`/`Tomorrow`/`This Week`/`This Month`/`All`; **`Upcoming` is the default on page load**, not `All`), with a per-row action `<select>` (Confirm/Cancel/Complete/No Show/Delete, replacing the old button group) instead of buttons — options are disabled per current status (`Confirm` only enabled when `Pending`; `Cancel` disabled once `Cancelled`/`Completed`/`NoShow`; `Complete`/`No Show` disabled until the appointment's own date+time has passed, mirroring the backend's time gate) and picking one fires the matching `PATCH`/`DELETE` immediately, resetting the select back to its placeholder. Both the Status filter and the Time filter apply immediately on `change` (no Search click needed for either) — picking a Status also clears the Time filter back to `All` first, since otherwise the default `Upcoming` bound would silently AND against the status filter and hide any `Completed`/`NoShow`/older `Cancelled` row (those can only exist in the past, by construction of the time-gate above). `patients.html`/`patients.js` (patients table — filterable by name/phone/MRN, read-only, each row's patient name is a link to `patient-profile.html?id=<id>`), and `patient-profile.html`/`patient-profile.js` (a single patient's info card plus their appointments split into "Next Appointments"/"Appointment History" tables, both fed by the one `GET /admin/patients/:id` call; each appointment row's patient-name link on `dashboard.js` uses `appointment.patient_id`, not `appointment.id` — the two are different numeric ids) — separate pages, not tabs on one page, linked via a shared icon sidebar (`.admin-sidebar` in `style/admin.css`, duplicated markup on both pages per the site's no-templating convention, with `.active` set statically per page). `admin-api.js` is the shared fetch wrapper: attaches the bearer token to every `/admin/*` call and auto-redirects to login on a `401`. `API_BASE_URL` is hardcoded separately in `admin-api.js` and `bookappointment.js` (two separate constants, not shared — deliberately not worth a shared config module for one string), currently both pointed at the deployed Render backend (`https://harmonysmiles.onrender.com/api`) rather than localhost — if the backend Web Service is ever renamed or redeployed under a different service name, both constants need updating to match, or every fetch from the deployed frontend silently fails.

## Deployment (Render)

The project deploys as three separate Render resources — a managed Postgres instance, the backend as a Web Service, and the frontend as a Static Site. Everything below was learned the hard way getting the first production deploy working; re-check this list first before assuming a fresh deploy problem is novel.

- **Root Directory must be set explicitly per service** (`backend` for the Web Service, `frontend` for the Static Site) — there's no root `package.json`, so an unset Root Directory makes Render's build fail immediately looking for one at the repo root.
- **Backend env vars are entirely separate from `.env`** — `.env` is gitignored and never reaches Render, so every var below has to be added by hand under the Web Service's Environment tab: `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_SSL=true` (see `db.ts`'s `ssl` option — required for Render Postgres, and easy to forget since local dev doesn't need it), and `JWT_SECRET` (`jwt.ts` throws at import time if missing, which crash-loops the whole service, not just the login route). Do **not** set `PORT` manually — Render injects its own and `server.ts` already reads `process.env.PORT`.
- **`server.ts` binds explicitly to `'0.0.0.0'`, not just a bare `app.listen(PORT, cb)`.** Without an explicit host, the app can start and log successfully while Render's external port probe still can't reach it — the deploy hangs for Render's full ~15-minute build/deploy time box, then fails with `Timed Out`, even though the process logs show it running fine the whole time. This is the single most misleading failure mode to debug here, since nothing in the app's own logs looks wrong.
- **`app.ts` has a `GET /health` route** returning `{ status: 'ok' }`, specifically so Render's Health Check Path (Settings → Health & Alerts) has a real endpoint to poll instead of relying on the bare port probe.
- **`db.ts`'s `connectionTimeoutMillis` is `10000`** (raised from an original `2000`) — 2 seconds was tight enough that a legitimate Postgres handshake (TCP + SSL negotiation + auth) across a real network path (e.g. seeding the DB from a home connection to a Render Postgres instance in a different country) would fail with `Connection terminated due to connection timeout` even though the raw TCP port was reachable (confirmed separately via `Test-NetConnection`). If this timeout ever gets dialed back down, expect this failure mode to resurface for anyone connecting from outside Render's own network.
- **Admin login credentials are not database credentials — don't conflate the two.** `DB_USER`/`DB_PASSWORD` are how the backend authenticates to Postgres; the admin dashboard login is checked against rows in the `admins` table, seeded separately via `npm run seed` using `ADMIN_USERNAME`/`ADMIN_PASSWORD`. A DB connection succeeding (no more 500s) but login still returning "Invalid username or password" means the `admins` table is empty or the seed script hasn't been run against *that* database yet — not a credentials-mismatch bug.
- **`seed.ts` is a one-off script, not part of the running service** — it's not something Render runs for you. Simplest path: run it locally, pointed at the production DB via Render Postgres's **External** hostname (not the Internal one, which only resolves from inside Render's own network) with `DB_SSL=true`, plus `ADMIN_USERNAME`/`ADMIN_PASSWORD`, as one-off `$env:` overrides for that terminal session rather than editing local `.env` (since `dotenv.config()` never overrides a var already present in `process.env`, session-scoped overrides safely take precedence without touching the file).
- **Frontend Static Site needs no build step** — empty Build Command, Publish Directory `.` (since `index.html` sits directly in `frontend/`). No env vars either; `API_BASE_URL` is compiled in as a literal string in the JS files (see Frontend section above), not injected at build/deploy time.
- Render's free Postgres tier is time-limited (deleted after a set period) — fine for testing, but the clinic's real data needs a paid instance.
- Free-tier Web Services spin down after ~15 minutes idle and take 30–60s to cold-start on the next request — expect the first booking/login attempt after a quiet period to look hung, not broken.

## Known limitations & recommended next steps

Found during a full-project audit; none of these block current functionality, but are worth picking up before this goes beyond local/single-clinic use:

- **No rate limiting anywhere** — `POST /admin/login`, `POST /appointments`, and `GET /available-slots` all accept unlimited requests per caller. The login endpoint is the highest-value target (bcrypt-protected password is still brute-forceable at whatever RPS the server allows). Add `express-rate-limit` (not currently a dependency) keyed by IP, at minimum on `/admin/login`.
- **`cors()` in `app.ts` has no options, so it allows every origin.** Fine for local dev; before deploying anywhere with a real frontend origin, pass an explicit `origin` allowlist. Not classic CSRF-exploitable today (auth is a Bearer token in a header, not a cookie), but it's still a defense layer worth adding.
- **No pagination on `GET /admin/appointments` or `GET /admin/patients`** — both return every matching row in one response. Fine at current data volume; will need `LIMIT`/`OFFSET` (or keyset pagination) once either table grows large.
- **No audit trail for admin actions** — confirming/cancelling/completing/marking-no-show/deleting an appointment doesn't record which admin did it or when (only `updated_at` changes, with no "by whom"). Add an `admin_id` column or a separate audit-log table if this is ever needed for accountability.
- **`getClinicNow()`'s `toLocaleString` round-trip** (`clinicTime.ts`) can theoretically misparse during the *server's own local* DST transition window (not Zurich's, which it already handles correctly) — narrow and currently unobserved; only matters if the server itself runs in a DST-observing timezone.
- Still no test framework/lint config anywhere in the repo (see "Commands" above) — not a regression, just worth remembering before assuming any change is "verified" by more than a manual `npm run build` + manual click-through.
